1. Introducción al Paradigma y Evolución Histórica

Concepto Central

¿Qué propone la Programación Orientada a Objetos?

Un paradigma de programación es un marco conceptual que organiza cómo modelamos datos, control de flujo y fronteras modulares. Mientras el estilo procedural estructura el programa como una secuencia de procedimientos que operan sobre registros (aun permitiendo modularidad y tipos abstractos), la POO agrupa estado interno y operaciones dentro de objetos gobernados por contratos explícitos.

  • Simula 67 (Dahl y Nygaard): introduce clases, instancias y subclases para simular sistemas físicos discretos.
  • Smalltalk-72/80 (Alan Kay, Xerox PARC): acuña el término Object-Oriented Programming centrado en el paso de mensajes.
  • C++ (1985), Python (1991), Java (1995), C# (2000+): llevan los objetos desde sistemas de alto rendimiento hasta arquitecturas multiparadigma modernas.

2. Fundamentos: Clases, Instancias y Referencias

Modelo de Ejecución en Python

Molde, Estado Independiente e Identidad

Una clase define la estructura y el comportamiento común; cada llamada a la clase ejecuta __init__ y produce una instancia con su propio diccionario o espacio de estado independiente. Las variables almacenan referencias hacia esos objetos: 

ana = CuentaBancaria("Ana Gómez", 30_000.0)
bruno = CuentaBancaria("Bruno Díaz", 15_000.0)
alias = ana  # No copia el objeto: referencia a la misma instancia

print(alias is ana)   # True  -> misma identidad en memoria
print(ana is bruno)   # False -> instancias independientes

3. Los Cuatro Pilares y Composición vs. Herencia

Pilar 1 · Abstracción

Contratos e Invariantes

Expone qué operaciones ofrece una entidad ocultando su representación física (ej. almacenar _kelvin >= 0.0 internamente mientras ofrece propiedades celsius y kelvin coherentes).

Pilar 2 · Encapsulamiento

Frontera de Validación

Impide mutaciones arbitrarias del estado. En Python, _saldo indica atributo interno por convención (PEP 8), mientras que __saldo activa name mangling (_Clase__saldo) para prevenir colisiones en subclases.

Pilar 3 · Herencia y Composición

Subtipado vs. Delegación

Reservá la herencia (class Sub(Base)) para relaciones genuinas de subtipado conductual («es-un»). Para reutilizar mecanismos sin exponer operaciones indebidas, preferí composición y delegación («tiene-un»).

Pilar 4 · Polimorfismo

Despacho Dinámico

Permite invocar el mismo mensaje (canal.enviar(msg)) sobre distintos tipos concretos y resolver en tiempo de ejecución el método específico sin cadenas rígidas de isinstance.

4. Principios SOLID y Patrones de Diseño

Cohesión y Bajo Acoplamiento

SOLID + Strategy, Adapter y Decorator

  • S (Responsabilidad Única): una clase debe tener una sola razón cohesiva para cambiar.
  • O (Abierto/Cerrado): extender comportamientos agregando nuevas clases sin editar código cliente estable.
  • L (Sustitución de Liskov): todo subtipo debe respetar las precondiciones, poscondiciones e invariantes del supertipo.
  • I (Segregación de Interfaces) y D (Inversión de Dependencias): depender de protocolos pequeños y abstractos en lugar de detalles concretos.
  • Strategy: encapsula algoritmos intercambiables en caliente dentro de un contexto (ej. políticas de descuento en Pedido).
  • Adapter y Decorator: traducen interfaces externas incompatibles o envuelven objetos para agregar responsabilidades sin explosión de subclases.

5. Compromisos (Trade-offs) y Comparación Multiparadigma

Criterio de Ingeniería

¿Cuándo evitar POO y cómo convive con otros paradigmas?

La POO no es una solución universal: crear jerarquías especulativas para problemas simples introduce complejidad accidental e indirección innecesaria. En scripts breves de extracción de datos, cómputo numérico matricial o tuberías de transformación pura sin estado, un diseño procedural o funcional suele resultar más directo y legible.

Tampoco deben repetirse mitos sobre memoria: un objeto no vive obligatoriamente en memoria dinámica (lenguajes como C++ o Rust alojan objetos por valor en la pila, y compiladores JIT devirtualizan llamadas monomórficas). En Python moderno, los tres paradigmas se complementan: objetos para resguardar fronteras e invariantes, funciones puras para transformar colecciones y algoritmos imperativos claros dentro de los métodos.

6. Notas de Ampliación y Bibliografía Académica

Ampliación 1 · Herencia Múltiple, Problema del Diamante y Algoritmo C3 MRO

Cuando una clase hereda de dos superclases que comparten un ancestro común (estructura en diamante), surge la ambigüedad sobre qué versión de un método debe ejecutarse primero. Python resuelve este problema de forma determinista mediante la linearización C3, consultable en Clase.__mro__, que preserva el orden local de declaración y garantiza monotonicidad cooperativa junto con super().

Ampliación 2 · Tablas Virtuales (vtable/vptr) vs. Búsqueda Dinámica en Python

En lenguajes compilados con tipos estáticos como C++, el despacho dinámico sobre métodos virtual suele implementarse mediante un puntero oculto por instancia (vptr) que indexa una tabla fija de punteros a función por clase (vtable) en tiempo constante O(1). En Python, cada instancia referencia su objeto clase (obj.__class__) y el intérprete resuelve atributos recorriendo diccionarios y el orden __mro__ con cachés especializadas en línea (PEP 659 en Python 3.11+).

Ampliación 3 · Proyección Arquitectónica: DDD y Arquitectura Limpia / Hexagonal

En sistemas de mediana y gran escala, los principios vistos en esta unidad sustentan el Diseño Guiado por el Dominio (DDD) —distinguiendo Entidades con identidad propia de Objetos de Valor inmutables— y la Arquitectura Hexagonal (Puertos y Adaptadores), donde el núcleo de negocio define protocolos (puertos) y la infraestructura externa (bases de datos, APIs HTTP, interfaces gráficas) se conecta mediante clases adaptadoras.
